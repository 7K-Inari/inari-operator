# Migrating from the inari-platform umbrella chart to the inari-operator charts

The operator and its CRDs are now released from this repo as two Helm charts
published to `oci://ghcr.io/7k-inari/charts`:

- `inari-operator-crds` — verbatim CRDs from `config/crd/bases` (group
  `platform.inari.io`), generated by controller-gen.
- `inari-operator` — the controller Deployment/RBAC/ServiceAccount.

Install order: **crds first, then the operator**. On upgrades, apply
`inari-operator-crds` before or together with `inari-operator`.

```sh
helm install inari-operator-crds oci://ghcr.io/7k-inari/charts/inari-operator-crds \
  --version <crds-chart-version> -n inari-system
helm install inari-operator oci://ghcr.io/7k-inari/charts/inari-operator \
  --version <chart-version> -n inari-system
```

`inari-operator`'s `appVersion` always matches the operator image released
from the same release-please run, and `image.tag` defaults to `appVersion` —
chart and image cannot drift unless you override `image.tag` explicitly.

## Adopting CRDs previously installed by the umbrella chart

If the cluster already has the `platform.inari.io` CRDs (installed by the
`inari-platform` umbrella via `templates/crds/inari-operator.yaml` gated on
`crds.inariOperator.enabled`), a plain `helm install inari-operator-crds`
fails with "invalid ownership metadata". Transfer ownership first:

```sh
for crd in argoprojects certissuers dnsrecords dnszones keycloakclients keycloakrealms tenantnamespaces; do
  kubectl label  crd "$crd.platform.inari.io" app.kubernetes.io/managed-by=Helm --overwrite
  kubectl annotate crd "$crd.platform.inari.io" \
    meta.helm.sh/release-name=inari-operator-crds \
    meta.helm.sh/release-namespace=inari-system --overwrite
done
helm install inari-operator-crds oci://ghcr.io/7k-inari/charts/inari-operator-crds \
  --version <crds-chart-version> -n inari-system
```

Helm 3.17+ alternative: `helm install --take-ownership ...` (or
`--set` equivalent on upgrade) adopts the resources without the manual
label/annotate loop.

## Switching the operator deployment

The umbrella's `inariOperator.enabled` stub and the new chart cannot run side
by side (same RBAC/SA semantics, different resource names). Cut over with the
image tag pinned so the running operator version does not change:

```sh
helm upgrade inari oci://ghcr.io/7k-inari/charts/inari-platform \
  --set inariOperator.enabled=false ...        # remove the stub
helm upgrade inari-operator oci://ghcr.io/7k-inari/charts/inari-operator \
  --set image.tag=<currently-running-operator-version> -n inari-system
```

## Version policy

- Chart versions (`inari-operator`, `inari-operator-crds`) are independent of
  each other and of the operator version — owned by release-please; never bump
  `version:` in `Chart.yaml` by hand.
- `appVersion` in both charts is bumped automatically by release-please
  (`extra-files` on the root go component) whenever an operator release is
  cut, so the CRDs chart's appVersion records exactly which operator release
  generated the CRDs.
- CI fails any PR where `config/crd/bases` (regenerated via `make manifests`)
  drifts from `charts/inari-operator-crds/templates`
  (`scripts/chart-crds-sync.sh --check`).
